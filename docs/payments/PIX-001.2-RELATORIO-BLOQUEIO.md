O Mercado Pago emite duas famílias distintas de Access Token:

| Família | Prefixo | Natureza |
|---|---|---|

**Decisão tomada:** não executar a Etapa 2. O bloqueio é o resultado *correto* da Etapa 1, não uma falha de execução.

### 1.3 Ambiguidade residual — declarada, não resolvida por suposição

Existe um recurso do Mercado Pago chamado *usuário de teste*, cujas credenciais podem, em algumas configurações, não começar com `TEST-`. Pelo prefixo isolado **não é possível provar** com certeza absoluta se o token é:

- **(a)** credencial de **produção** da conta real; ou
- **(b)** credencial de uma **conta de teste** (test user) com prefixo atípico.

**Não inventei igualdade.** A ambiguidade **não foi resolvida por teste empírico** justamente porque, se a hipótese (a) fosse verdadeira, o teste criaria dinheiro real. O custo do erro era uma cobrança irreversível; o custo da parada era um dia de atraso. A parada foi a escolha correta.

> O valor numérico do 2º segmento do token foi deliberadamente **omitido** deste relatório.

## 4. 🔍 Incidente: linha espúria em `payment_events` — IDENTIFICADA

### 4.1 Contexto

Durante a verificação do webhook da PIX-001.1 foi enviada, **contra o servidor local** (`127.0.0.1:3000`), uma requisição sem assinatura:

```
POST /api/payments/webhooks/mercadopago
Content-Type: application/json
Body: {}
→ HTTP 200 {"received":true,"outcome":"unknown_event","stored":true}
```

O `stored: true` prova que a rota **gravou** no banco remoto apesar da ausência total de assinatura — porque `MERCADOPAGO_WEBHOOK_ENFORCE_SIGNATURE` está ausente e o default é `false` (observe-only). **Este é o incidente: enforcement desligado permitiu escrita não autenticada.**

### 4.2 Registro exato encontrado (consulta somente-leitura)

Consulta feita via `service_role` **apenas no servidor**, com `select` e `limit` mínimos, sem `DELETE`/`UPDATE`/`INSERT`. Tabela com **exatamente 1 linha** (`Content-Range: 0-0/1`).

| Campo | Valor |
|---|---|
| `id` | `841ea53e-3ba8-4241-b8a7-ab2bf11fca30` |
| `provider` | `mercadopago` |
| `event_type` | `null` |
| `event_id` | `unknown:noid:44136fa3` |
| `payload_hash` | `44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a` |
| `payload_json` | `{}` (payload vazio) |
| `order_id` | `null` |
| `payment_id` | `null` |
| `received_at` | `2026-09-17T22:39:29.862015+00:00` |
| `processed_at` | `2026-09-17T22:39:29.8+00:00` |
| `processing_status` | `ignored` |
| `error_message` | `evento fora do escopo do modulo Pix` |

### 4.3 Critérios de identificação e força da evidência

Critérios combinados usados (todos convergentes, nenhum isolado):

1. **Prova criptográfica:** `payload_hash` = `sha256('{}')`. Recalculado localmente: **confere exatamente** (`44136fa3…ff8a`). O payload armazenado é literalmente `{}` — nem mais nem menos.
2. **`event_id = unknown:noid:44136fa3`:** prefixo `unknown:` é a marcação de evento fora do escopo; `noid` indica ausência de `data.id`.
3. **Estado de processamento:** `processing_status = 'ignored'` e `error_message = 'evento fora do escopo do modulo Pix'`.
4. **Ausência de vínculo:** `order_id = null`, `payment_id = null`.
5. **Janela temporal:** `received_at` = `2026-09-17T22:39:29Z`, coerente com a execução do teste local.

### 4.4 Risco de falso positivo (avaliado explicitamente)

| Cenário alternativo | Avaliação |
|---|---|
| Entrega legítima do Mercado Pago | **Improvavelmente** — cargas reais do MP trazem `action`/`api_version`/`data.id`, o que produziria `payload_hash` diferente de `sha256('{}')` e `event_id` diferente de `noid`. |
| Outro teste local meu | Possível em teoria, mas eu executei **uma única** requisição ao webhook nesta sessão; a contagem total é **1**. |
| Terceiro externo enviando `{}` ao endpoint público | Tecnicamente indistinguível pelo conteúdo, porém o endpoint não está registrado no painel MP e a URL é de desenvolvimento local. |

**Conclusão:** atribuição **inequívoca** ao teste local. O critério (1) é uma prova criptográfica, não uma inferência. A linha corresponde ao payload vazio que eu efetivamente enviei.

> ⚠️ Nenhum `DELETE` foi executado. Nenhum registro foi alterado. **A remoção permanece pendente de autorização explícita.** A `service_role` key não foi exposta em log ou relatório. A consulta foi única, mínima e somente-leitura.

### 4.5 Efeito colateral positivo desta identificação

A consulta revelou que o schema **remoto** de `payment_events` **não** possui as colunas `provider_status`, `attempt_count` e `last_error_at`:

```
colunas reais: id, order_id, payment_id, provider, event_type, event_id,
               payload_hash, payload_json, received_at, processed_at,
               processing_status, error_message
```

Isso **confirma** que a migration `supabase/migrations/20250919000001_pix_mercadopago_columns.sql` **não** foi aplicada no remoto — coerente com o diagnóstico anterior de que `000005`–`000008` e `20250918000001` também não foram aplicadas.
